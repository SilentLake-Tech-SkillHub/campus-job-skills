# 公司交接：正向评审与反向评审

搜索端与投递组件之间只通过 `岗位交接/` 的固定文件交接（见 [数据建设与固定流程](storage-workflow.md)）。批次状态：空闲/已回写 → 等待正向评审 → 已交接 → 等待反向评审 → 已回写。

## 固定编码

身份一律用固定编码，第一次出现时按固定规则分配、只增不复用（计数器在主数据 `编码计数器`）：公司 `C00001`（「公司主数据」表，按公司名或用户确认过的别名精确匹配）、站点 `S0001`（「投递站点」表，同一公司下按 https 域名匹配；新域名即新站点，旧站点标“停用”）、岗位 `J000001`（地区岗位表的「岗位编码」列）。链接、名称、官方岗位ID都是值：链接或页面元素变了只刷新值，编码不变。其他各表（校招主链接、校招计划、投递名额等）只加「公司编码」列。确认台账、链接例外、投递回传都按编码记。

## 正向：主表 → 投递组件

1. `company_store.py refresh`：按主表覆盖重建 `公司/<公司编码>.json`（每家公司一份宽表：「站点」「岗位」是主表投影，「批次」是本轮选岗与确认），并给每个岗位定志愿分组：该公司“投递名额”表“公司总量”行的“是否分BU可平行投递”为“是”时按所属BU分组（BU未披露归“公司”），否则整家公司一组。宽表只能由本脚本生成，改值只能改主表再 refresh。
2. 志愿顺序：同一分组有多个待投递岗位时，向用户展示分组和岗位，由用户给出顺序；`company_store.py set-order --input <[{code: 岗位编码, 志愿顺序}]> --quote "<用户原话>"` 写进主表（分组内不重复的正整数，同组一次给全；第1志愿已投递时本批可以从2起）。Agent 不替用户排顺序。
3. `company_store.py forward`：从[一次性需求表](application-requirements.md)读取本轮公司范围；空需求默认最新10家公司，保留各公司全部“岗位待投递”岗位。写入各公司宽表的「批次」（等待正向评审）与 `正向评审.html`，读回后立即清空临时需求；失败保留。链接、已确认链接例外及志愿顺序由固定脚本核对，未通过的岗位在评审页“本批不交接”列出原因。
4. 把评审页给用户看；用户明确确认后 `company_store.py forward-confirm --quote "<用户原话>"`（逐家登记原话与该公司的内容指纹，批次 → 已交接）。内容指纹只覆盖本批选中岗位的执行字段及其站点，只当核对字段用；一家被改只让这一家失效。
5. 投递组件的 `role_queue_import` / `company_batch_create` 只读取已交接且确认后未被改动的公司文件；Hook 同样拦截。上一批未完成反向评审前不能生成下一批。

材料种类只在 `references/role-materials.json` 定义（主表列、分隔符、“明确没有”的写法、取值格式），key 与投递组件 `catalog/role-materials.json` 一致；新增材料两边各加一项。每岗位的 `材料` 契约：推荐码原文、解析值、证据（岗位编码、主表列、该单元格内容的 Hash）与“有则必填”条件。没有代码与待核实分别标识，个人主档和公司配置不复制代码。

## 链接刷新

每个岗位只有一个岗位链接和一个投递链接，存在主表 J 行；每个站点只有一个登录链接和账号核对页，存在「投递站点」S 行。链接只在三种情况下刷新：打开失败；第一次拿到一个空着的链接；岗位链接打开后跳到编号不同的岗位页、且岗位名一致（观察值就是跳转后的岗位页，预览时直接作为新链接）。编号不变的跳转不算变化。

1. 投递端只在 `投递回传.json` 的 `observations` 里按编码记一条观察（字段、观察到的值、证据），不改交接区。
2. `company_store.py apply-observations` 生成预览（“J000184 投递链接：空 → X”）；岗位链接打不开时列在 `waiting_for_new_link`，由搜索端重新找到官网岗位页后用 `--input <[{code,new_link}]>` 给出新链接。
3. 用户确认后 `apply-observations --quote "<用户原话>" --expected-sha <预览摘要>`：在原编码下覆盖主表的值，只重生成受影响的公司宽表；在本轮批次中的公司按“链接”作用域重新确认（记上一版指纹）。投递端用 `company_batch_refresh_materials` 只刷新这几家。

批次外的岗位换链接用 `json_excel_sync.py relink`；单独补投递链接用 `set-apply-link`（须与岗位站点同域）；站点的登录链接与账号核对页用 `set-site-links`。都先 `--preview` 给用户看，再带原话执行。

## 作用域确认

确认按作用域保存：`确认.scopes.selection`（正向评审确认选岗）、`materials`（补充材料）、`links`（链接变更）各保留最新一条，互不覆盖；顶层 `userQuote/confirmedAt/contentSha256/scope/previousContentSha256` 是当前生效的门禁。确认后的任何局部变更都必须声明自己的作用域，只改该作用域字段，只让依赖它的冻结状态失效，并保留其他作用域的确认原话。

当前批次补充材料使用 `company_store.py amend-materials` 先预览；用户明确批准后以 `--expected-sha <预览原摘要> --quote "<用户原话>"` 执行。只补已确认岗位材料，不改变岗位、链接、顺序、批次编号或主表状态。投递端随后用 `company_batch_refresh_materials` 更新这一家，保留原任务，旧冻结计划和完成核验必须重新生成。

## 反向：投递组件 → 主表

1. 投递组件 `application_closeout` 校验官网证据后把每个岗位的最新结果按岗位编码覆盖写入 `投递回传.json`（不改主表）。
2. `company_store.py reverse`：读回传，逐行给出“当前状态是X，更新状态是Y”（确认投递 → 岗位已投递；官网确认关闭 → 岗位失效/关闭），不确定、受阻、跳过的结果只列出不改状态；生成 `反向评审.html`，有结果的公司批次 → 等待反向评审。
3. 原样把变更给用户看；用户确认后 `company_store.py reverse-confirm --quote "<用户原话>"` 写主表（记确认台账）并清除已处理的回传。不确定或受阻的结果在用户处理前保留，重新导入时对应岗位受保护不重跑；用户处理后用 `--resolved <岗位编码>` 清除。逐家推进：某家只处理了部分岗位时保持“进行中”，沿用原岗位与确认指纹；本轮各家都已处理才算本轮结束，才能生成下一批。「批次」的 `进度` 只存执行进度，不进入内容指纹；不能借此更改岗位、顺序或材料。反向确认不会清掉待确认的链接观察。

选岗、去留、志愿顺序 100% 由用户决定；Agent 只展示与建议，不按名额提前淘汰任何符合要求的岗位。
