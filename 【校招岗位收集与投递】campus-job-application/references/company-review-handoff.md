# 公司机会核对与搜索—投递交接（v1）

搜索主流程、偏好确认、计划盘点、内推查询、并行交付、投递 Prepare/续跑都读取本契约。Excel 是主记录；HTML 是用户核对视图；JSON 是 Excel 的同版本交接导出，不是独立编辑的状态台账。实际数据、确认原话和材料只留私有工作区。

## 1. 搜索端交付

在用户批准的公司、地区与招聘周期内，先盘点全部适用计划（普通校招、产品培训生、管培生、技术专项等名称以官方为准），再遍历这些计划的完整岗位目录，列全岗位名称、计划、BU、地点与可核实链接。目录不先按岗位偏好裁剪；岗位族/城市硬范围决定候选，不删除目录事实。目录可记录不相关岗位，不把它们写成地区表的可投候选。对候选及边界岗位读取完整 JD；目录中无详情直链的记录保留结果页及缺口，不猜 URL。按官方岗位 ID 去重，多计划出现的同一岗位保留全部计划关系，一个多城市岗位只计一次。计划数量分“已发现数/覆盖是否完整”，目录未读全不可称全部岗位。

已访问公司的历史缺口仍按原首轮/指定补查规则处理。本次流程升级不授权重查所有旧公司；当用户选择该公司进入投递时，补齐其交接所需具体缺口。公司全量目录与规则取证属于搜索端，投递端负责接受、时效及账号读回，不临时重做首轮。

## 2. 三档候选与推荐

- 完全符合：命中本批用户明确提出的岗位职责类型，逐岗关联用户需求原话及 JD 依据。
- 部分符合：同属关注方向但具体职责、客群或倾向存在差异，说明符合点和差异，软偏好不能用作硬排除。
- 特殊计划：展示培养目标、轮岗/定岗、学历专业技术要求、届别、周期地点、名额占用及条件，再询问用户是否考虑。计划用户决定为考虑/不考虑/待确认；未答复不纳入推荐或选择。特殊计划里的岗位还要记录职责符合程度。

目录、三档候选、Agent 最终推荐、用户最终选择是四层信息。个人资格另记符合/不符合/待核，三档不是能力分或资格通过。建议与最终选择允许不同；Agent 不替用户选择。候选保留完整 JD、来源/日期、资格依据、BU 或未披露、城市及就业性质。硬条件冲突或未知需原有具体尝试指令；不把“完全符合”当作可直接投递。

## 3. 投递规则矩阵

搜索阶段逐项查：公司总量、计划内限额、跨计划共享/互斥、投递轮次及各轮窗口/上限/重置、每 BU 上限与跨 BU 共享、同时流程数和志愿顺序、冷冻期触发动作/持续时间/影响范围/解除条件、换岗/撤回/被拒后名额与再次申请影响。每项保留官方原文、来源、核验时间、适用范围、共享名额组及关系。无 BU 限制时仍明确公司总上限；不把缺失 BU 规则当无 BU 划分。

规则逐项标已核实/未核实/不适用。未核实要写已查来源与待核事实；不适用也须依据。不猜轮次重置，不把多个上限相加，不把空白当无限制。不登录可查的先查齐；账号剩余名额在经授权的登录后核实。HTML 区分公开上限与当前账号已用/剩余。

最终推荐与用户选择均须符合全部适用约束：公司、轮次、计划、BU 及共享组。未知限制需在 HTML 明示，由用户针对未知项明确决定并在投递端实时复核；未知时沿用投递端“仅首岗、首次提交后读回再确认下一岗”规则，不伪造批量可投。冷冻期生效或名额不足不默认执行。

## 4. 内推码在搜索端查齐

HTML 交付前调用内推查询。按招聘主体、周期、计划、BU、岗位类别记录码及大小写、来源、核验日期、有效期、适用范围与冲突。不把一个码抄到不适用计划/BU。已核实/未找到/未核实/不适用均需查证记录；“查齐”是所有适用范围有结论，不保证一定存在有效码。大陆默认牛客→官方→其他公开渠道，官方冲突优先；其他地区查官方推荐要求，不适用时明确记载，不为找码扩展至私信/加群/付费。投递端只在过期、范围冲突或表单变化时回查并同步。

## 5. Excel、HTML、JSON 与确认

在既有主工作簿增加五张共享明细表（不是每公司建表）：公司核对、计划明细、岗位目录、投递规则、内推信息。字段见随包 `scripts/company_handoff.py` 的 SCHEMA；已有地区表、校招计划、校招主链接、投递状态枚举保持。公司核对存批次/公司身份、版本、已查范围/缺口、需求、推荐理由与确认证据；其余表按公司键和条目键关联，长 JD 超过 Excel 单元格限制时明确报错，分段设计后才能继续，不截断。地区表仍保存候选与真实提交状态；选择和推荐在岗位目录分别保存。首次迁移只补用户选中的公司，不清空旧记录或将未确认历史批次冒充已确认。

HTML 从已保存并读回的 Excel 生成，按公司展示：计划及要求→完整岗位名称目录→三档候选及完整 JD→最终推荐与理由→轮次/BU/公司限制及冷冻期→内推码→用户最终选择与待确认项。所有现有公司相关数据一并附上（既有地区岗位行、计划、入口、提交状态），明确数据时间/版本、未核实事项和覆盖缺口。带来源的外部文本转义，链接只允许 http/https，页面不执行申请、不包含自动提交按钮。

用户完整核对后，先把调整后的最终选择、顺序与计划决定写回 Excel；若与所见 HTML 不同先重新生成供其核对。仅在明确确认当前公司版本后记录确认原话的私有证据路径、时间、当前业务数据摘要和已展示 HTML 哈希，再导出 JSON。无回复、浏览页面、Agent 推荐或勾选本地控件都不是确认。

JSON 固定在工作簿同目录 `岗位交接/<批次>/公司方案.json`，HTML 为同目录 `公司核对.html`；草稿导出带待确认，不可执行。每次刷新必须按“备份→读最新Excel→最小更新→保存读回→重导JSON/HTML→校验”完成，版本同步。导出带整本Excel SHA256及数据摘要；Excel任何更改后旧JSON不可用于下一申请动作。刷新内容改变则新版本、受影响公司旧确认失效；不影响业务选择的纯文件/状态刷新可重导并保留原确认，原已投及回执不得重置。历史版本及确认文件保留。

双文件写入中断时保留旧版本/备份，禁止使用不同步文件，重新从Excel导出恢复；不反向从旧JSON覆盖Excel。多人只由协调者写Excel与JSON。渲染完成不等于已展示，脚本验证不证明用户真的确认、官网覆盖完整或规则理解正确，执行者必须核对原始证据。

## 6. 投递端接收

Prepare 前：检查Excel/JSON哈希及内容一致、对应公司已确认、HTML版本和确认原话存在、具体岗位在用户最终选择中、特殊计划已考虑、完整JD/资格证据、规则和内推结论齐全，选中岗位必须对应既有地区表同公司/直链/标题/BU/地点/JD。任一失败返回搜索侧补齐该缺口，其他独立公司可继续。

接收时将同一确认原话引用到既有 `次序确认.md`、需要时的 `用户选岗.md` 和 `选岗确认.md`，写明来自已确认的公司HTML版本；这些是门禁兼容索引，不是再次向用户索要批准。数量规则文件从同版矩阵提取并保留各层限制，不能将BU上限冒充公司总上限。研究HTML确认可复用为公司次序/选岗依据，不要求用户重复确认同一事实；投递Query只补材料、准备授权、执行方式等未答项目。一般选岗授权不允许替换已确认方案；新推荐须重新HTML确认。接收后仍读回当前账号历史/名额，遇冲突、失效码或变化先回写Excel并同步JSON，必要时更新HTML重新确认。Review 的表单版本批准和每次Submit的确切目标确认仍执行，研究确认不授权最终提交。

## 7. 工具与验证

两套技能包携带相同 `scripts/company_handoff.py`，同步修改并比对哈希。它的命令：`write --workbook ... --batch ... --input <草稿JSON>`（只更新本批给定公司，清除其旧确认）、`export`（从Excel读回生成JSON和HTML）、`confirm --company <公司键> --evidence <相对工作簿目录的确认文件> --html-sha256 <用户看过的HTML哈希>`、`check --url <岗位直链>`。所有命令带 `--workbook` 和 `--batch`。confirm 只能在用户确认后执行；不能自行创建用户确认原话。write 输入为 `{ "companies": [...] }`，字段与导出结构相同；它是临时交换输入而非长期第二台账。脚本仅更新五张明细表，候选地区行/原有计划与入口仍按工作簿契约先写入。

测试覆盖：目录外岗位不漏列、特殊计划未考虑不可选、推荐与用户选择不同、分轮次/BU/共享名额超限、缺内推查证、缺确认、篡改JSON/HTML/确认文件、Excel刷新陈旧导出、旧确认失效及地区表不一致。真实网站/账号规则仍需现场核验。

转换与存储由搜索端生成、投递端接收并刷新。支持先组织 UTF-8 草稿 JSON，再用 write 写入既有 Excel，随后读回导出同版本 JSON/HTML；也可先更新 Excel 后 export。JSON 覆盖本批公司方案及相关既有行，不是任意工作簿的无损序列化。真实数据和历史备份均在私有工作簿旁，不写入 Skill。此工具不是后台文件监听器；手动改 Excel 后必须 export，陈旧快照会被 check 阻断。所有 JSON/HTML 文本按 UTF-8 读写。
