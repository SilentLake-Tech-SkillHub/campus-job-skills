# 选岗范围与偏好

查询、计划盘点、筛选、汇报和续跑都按本文件执行。用户的实际取值只在工作区 `产品管理/求职目标.json`，本文件只定义怎么用。

## 唯一来源

- 岗位顺位、排除红线、城市范围与优先级、用工类型、特殊通道、决策红线、在用简历，全部以 `产品管理/求职目标.json` 为准。
- 用户纠正时直接改写该文件对应条目（覆盖旧内容），不另记纠正日志、不保留旧版本。
- 本批特有的选择（公司范围、信息收集还是准备投递、一个还是多个 AI）在对话中确认，只对本批有效，不写成长期规则。

## 硬范围与排序分开

- 硬范围（排除红线、城市限制、用工类型）决定岗位是否在范围内，用于官网筛选和纳入判断。
- 顺位和城市优先级只决定展示顺序，不缩小搜索范围；低优先级的岗位仍在范围内，不能当作排除。
- 不同维度之间不做加权合成；有冲突时把双方的 JD、城市、用工事实列给用户决定。

## 标题＋完整 JD

标题和分类用来发现岗位，是否纳入由完整 JD 的实际职责决定。不能只凭标题纳入或排除；完整 JD 打不开的标为待核，不用摘要代替。

## 岗位身份

- 同一家公司内优先用官方岗位 ID 识别岗位，没有 ID 时用规范化的详情页链接（只去掉 utm_*、ref、source 等跟踪参数）。
- 同名但 ID、BU 或城市不同的岗位分开记录；一个官方 ID 对应多个城市只记一行。
- 身份不确定时保留待核，不编造 ID 或链接。

## 逐岗汇报

每个已核岗位汇报：公司、岗位、直链、BU（无则“未披露”）、官方城市、用工类型、方向、决定性的 JD 依据、纳入/排除/待核理由、资格结论与缺口。被排除或待核的岗位同样保留理由，不计入已核。

## 决策红线

- 选岗、去留、投递顺序 100% 由用户决定；Agent 只展示和建议。
- 不得因名额提前剔除任何符合要求的岗位；只列出符合要求的岗位和公司的名额限制。名额收口只在用户的选择占满“公司总量”后由固定脚本执行。
- 已投递的岗位和用户明确的选择不因偏好更新而撤回、重投或替换。
